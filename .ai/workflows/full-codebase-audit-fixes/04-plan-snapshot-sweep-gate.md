# Plan: Snapshot Sweep Gate

## The Plan

This slice writes almost no code. Its entire job is attribution — proving that every pixel that
changed in the Paparazzi goldens changed for a reason we can name. The content slices do the
math; this slice counts the damage and signs off on the bill.

The working tree has two surprises that materially shape the plan. First, the
`isometric-compose/src/test/snapshots/` directory is untracked — it exists on disk with 29
PNGs from some prior record pass (during WS10 / depth-sort work, not the sweep), but it has
never been committed. This means CI is not currently running Paparazzi verification at all:
there is nothing to verify against. The directory must be committed as part of this gate, and
the record pass that produces the committed goldens must happen after all six content slices
land. Second, `docs/assets/screenshots/grid.png` and `multiple-shapes.png` are modified in
the working tree — they were regenerated by an earlier `DocScreenshotGenerator` run and left
unstaged. The sweep-gate's DocScreenshotGenerator step overwrites them cleanly after all
content-slice geometry is in place.

The attribution ledger is the methodological heart of this plan. The expected-change set going
into the record pass is exactly: `octahedron.png` (B1), `knot.png` (B2), `sampleThree.png`
(B1 composite scene), and conditionally `alphaSampleScene.png` (G1, only if Group alpha
affects that scene's rendering). Every other golden in the 29-file set should come out
byte-identical after record. Any that does not is an unattributable regression, and the
resolution is never "re-record harder" — it is to reopen the owning content slice.

The cross-platform drift is real but bounded. Paparazzi 1.3.0 has known pixel-level differences
between Windows record hosts and Linux CI verify hosts (issues #1465, #1716). Local green does
not close the gate; CI `verifyPaparazziDebug` on the record commit does. If CI fails on
drift-only pixels, the decision between "record on a CI-matching platform" and "set a minimal
deliberate `maxPercentDifference`" is explicitly PO-DECISION-PENDING — staged here so verify
never improvises past it.

## Proposed Change Strategy

The attribution-ledger method: before the record pass, establish the expected-change set from
the content-slice plans. After the record pass, diff every golden against the pre-record state
(using `git diff --stat` on the snapshots directory). Build a table: golden file → expected
owning fix → actual change (diff present / byte-identical) → verdict (attributed / unattributed).
A golden that shows a diff but is not in the expected-change set is a regression that blocks
the slice. A golden in the expected-change set that shows no diff means the owning fix did not
produce visual output — investigate whether the fix is correct before accepting "no change" as
a pass. A golden not in the expected-change set that is byte-identical is confirmed clean.

The doc-screenshot strategy is simpler: `./gradlew :isometric-core:test --tests "*.DocScreenshotGenerator.generateAll"` re-renders all 16 doc screenshots through `AwtRenderer`. The geometry-affected outputs (shape-octahedron.png, shape-knot.png, complex-scene.png) will change for B1/B2 reasons. The remainder should be stable relative to the last committed regen.

## Freshness Research

**Paparazzi 1.3.0 record/verify semantics:**
- Source: cashapp/paparazzi GitHub repository, 1.3.0 release and issues tracker (informed by prior shape-stage research).
- `recordPaparazziDebug` task: writes PNGs to `src/test/snapshots/images/`. `verifyPaparazziDebug` task: reads from the same location and fails the build if any test's rendered output exceeds the tolerance. `./gradlew test` automatically selects verify mode when the directory is present and non-empty — it does not require an explicit `verifyPaparazziDebug` invocation.
- **Cross-platform drift (issues #1465, #1716):** Paparazzi uses `BufferedImage` / Java2D rendering under the hood. Java2D font rendering, antialiasing, and sub-pixel geometry differ between JVM implementations and OS rendering pipelines. Windows JDK Temurin 21 vs ubuntu-latest Temurin 21 can produce ~0.1–2% pixel-level differences on the same scene geometry, even without code changes. The issues are open as of Paparazzi 1.3.x and are not fixed in 1.3.0.
- **`maxPercentDifference` in Paparazzi 1.3.0:** This is a **per-test parameter** on the `Paparazzi()` rule constructor: `Paparazzi(maxPercentDifference = 0.5f)`. It is NOT a global build-level setting. To set it globally, a shared constant in the test class or a base test harness is needed. The 1.3.5+ releases may have a global config option — out of scope for this sweep (toolchain upgrade is explicitly out of scope per shape).
- **Community mitigation:** The most common community approach is either (a) setting a small `maxPercentDifference` globally via a test harness, or (b) recording goldens on CI (the same platform that verifies). Both options are valid; (b) is the "correct" long-term solution but adds per-record operational cost.
- **Takeaway for this plan:** Local record + CI verify is the planned flow. `maxPercentDifference` is the staged fallback if drift-only CI failures occur. The decision is PO-DECISION-PENDING because the specific failure mode is not yet observed.
