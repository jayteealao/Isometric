# Plan: Docs & Housekeeping

## The Plan

Three predecessor slices have landed — depth-correctness, interaction-api-honesty, and view-module — and this slice's job is to make the written word catch up with everything they changed. The work falls into three independent tracks that can proceed in any order: KDoc corrections in source files (L1, L2, and deferred-from-code-slices prose); site doc updates authored in `site/src/content/docs/**/*.mdx` and mirrored to `docs/` via `scripts/sync-docs.js`; and two hygiene items (L9 ghost dirs/tarball, L10 Compose version catalog) that have no doc dependencies and can commit first.

The KDoc side has two genuinely wrong pieces of information still in the codebase. The L1 finding is that `Point.kt` and `IsometricEngine.kt` both describe the +x axis as "right-and-down" when the projection formula shows the opposite — increasing x decreases screenY (y coordinates go up on screen, not down). Correcting this is a one-paragraph KDoc change that needs to survive the "right-and-down" intuition: the formula `screenY = originY − x·scale·sin(α)` is the proof inline in the KDoc diagram. L2 is a one-liner: `Vector.normalize()` says "Throws if magnitude is zero" but returns a zero vector since commit eea28bb; the KDoc needs one word changed.

The site doc changes are more numerous but individually small. The non-default-angle depth formula reference in `coordinate-system.mdx` and `depth-sorting.mdx` still cites the old broken formula `x·cos(α) + y·sin(α) − 2z`; it becomes `(x+y)·sin(α) − 2z`. The `NoDepthSorting` entry in `depth-sorting.mdx` should explicitly contract insertion order (L3 behavior change). `scene-config.mdx` needs a projectionVersion requirement note for custom `SceneProjector` implementors (A2), and the `@Stable` (not `@Immutable`) annotation update for `SceneConfig` (M3). The drag guide examples must match the landed H1 fix — the "linear v1 approximation" language is gone; code examples should state the delta is in screen pixels (the contract is unchanged, but the old misleading comment must not remain). The shapes guide gets a note that Pyramid is now solid (M6). The hit-testing guide documents that TileGrid clicks work with a standard engine and the projectionVersion contract for custom projectors.

The top risk is vocabulary leak. This slice writes more prose than the three code slices combined, and every commit message and new doc paragraph must stay in product language — the external-output boundary rule is in force for every file. The secondary risk is sync discipline: `docs/*.md` must be regenerated by `scripts/sync-docs.js`, never hand-edited.

## Assumptions

All autonomous implementation-detail decisions made under the AUTONOMOUS OVERRIDE policy:

1. **L1 corrected axis description: "right-and-up" not "right-and-down".** The projection formula `screenY = originY − x·scale·sin(α)` proves that increasing x decreases screenY, meaning +x moves a point upward on screen (in addition to rightward). The current "right-and-down" KDoc is factually wrong. The correction is mathematically necessary, not a scope call.
